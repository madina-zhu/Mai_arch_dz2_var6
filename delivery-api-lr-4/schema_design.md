# Обоснование проектирования схемы данных (Schema Design)

## 1. Встраивание (Embedding) массива `events` в документ доставки
**Решение:** Хранить историю событий доставки (`events`) как встроенный массив поддокументов внутри документа `deliveries`.

**Обоснование:**
- **Локальность данных и производительность чтения:** История перемещений запрашивается в 100% случаев при отслеживании посылки. Встраивание позволяет получить полную историю за один запрос к БД (one round-trip).
- **Логическая целостность:** События не имеют самостоятельной ценности вне контекста конкретной доставки.
- **Паттерн:** Используется паттерн **Embedded Document**.

## 2. Встраивание (Embedding) массива `features` в документ посылки
**Решение:** Хранить особенности посылки (`features`) как встроенный массив строк внутри документа `parcels`.

**Обоснование:**
- **Простота и эффективность:** Особенности — это простой список строк, не требующий отдельной коллекции.
- **Атомарность обновлений:** Добавление/удаление выполняется одной операцией.

## 3. Ссылка (Reference) на `sender_id` и `receiver_id`
**Решение:** Хранить только идентификаторы отправителя и получателя в MongoDB, а полные данные пользователей — в PostgreSQL.

**Обоснование:**
- **Гибридная архитектура:** Пользователи управляются в PostgreSQL.
- **Избежание избыточности данных:** Встраивание привело бы к дублированию.
- **Масштабируемость:** Документы в MongoDB остаются легковесными.

## 4. Полиморфизм через опциональные поля
**Решение:** Использовать опциональные поля в документах для различных типов доставок.

**Обоснование:**
- **Гибкость:** Разные типы доставок могут иметь разные атрибуты.
- **Расширяемость:** Новые типы можно добавлять без миграции схемы.
