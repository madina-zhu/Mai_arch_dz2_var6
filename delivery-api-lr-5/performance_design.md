# Performance Design: Caching & Rate Limiting Strategy

## 1. Анализ производительности (Performance Analysis)

### 1.1. Определение "горячих путей" (Hot Paths)

1.  **Поиск доставок (`GET /deliveries`)**:
    - **Параметры:** Фильтрация по отправителю (`sender_id`), получателю (`receiver_id`), трек-номеру (`tracking_number`).
    - **Частота:** Высокая. Пользователи часто отслеживают свои посылки.
    - **Характер нагрузки:** Read-heavy (чтение преобладает над записью).

2.  **Поиск пользователей (`GET /users`)**:
    - **Параметры:** По логину или маске имени/фамилии.
    - **Частота:** Средняя.

3.  **Аутентификация (`POST /login`)**:
    - **Риск:** Подвержена brute-force атакам.

### 1.2. Определение медленных операций (Bottlenecks)

1.  **Сложные запросы к MongoDB (`GET /deliveries`)**:
    - Запросы с фильтрацией по `sender_id`, `receiver_id` требуют сканирования индексов.
2.  **Запросы к PostgreSQL (`GET /users`)**:
    - Поиск по маске имени/фамилии ресурсозатратен.

### 1.3. Требования к производительности

- **Время отклика (Latency):**
  - P95 для `GET /deliveries`: < 100 мс
  - P95 для `GET /users`: < 50 мс
  - P95 для `POST /login`: < 200 мс
- **Пропускная способность:** минимум 1000 RPS на чтение доставок

## 2. Проектирование стратегии кеширования

### 2.1. Выбор данных для кеширования

| Данные | Обоснование |
|:---|:---|
| **Списки доставок** (`GET /deliveries?sender_id=...`, `GET /deliveries?tracking_number=...`) | Часто запрашиваются, данные меняются редко |
| **Профили пользователей** (`GET /users?login=...`) | Данные почти статичны |

### 2.2. Стратегия кеширования

Используется **Redis** со стратегией **Cache-Aside (Lazy Loading)**.

#### Пример: поиск доставок по отправителю

1. **Чтение:**
   - Запрос `GET /deliveries?sender_id=123&from=1&to=50`
   - Ключ кеша: `deliveries:sender:123:1:50`
   - **Hit:** возврат из Redis
   - **Miss:** запрос к MongoDB → сохранение в Redis → возврат

2. **Запись/Обновление:**
   - При создании новой доставки (`POST /deliveries`) → инвалидация кеша по `sender_id` и `receiver_id`

### 2.3. Параметры кеширования

- **TTL для доставок:** 60 секунд
- **TTL для пользователей:** 300 секунд (5 минут)

### 2.4. Инвалидация кеша

При успешном `POST /deliveries`:
- Удаляются ключи `deliveries:sender:{sender_id}:*`
- Удаляются ключи `deliveries:receiver:{receiver_id}:*`

## 3. Rate Limiting

### 3.1. Защищенные endpoints

- `GET /deliveries` — защита от массового скачивания данных

### 3.2. Параметры

- **Алгоритм:** Token Bucket
- **Лимит:** 100 запросов в минуту
- **Заголовки:** `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`

### 3.3. Ответ при превышении

`429 Too Many Requests`

---

## 4. Ожидаемые результаты

| Метрика | Без кеша | С кешем |
|:---|:---:|:---:|
| Время отклика P95 | ~50 мс | ~5 мс |
| Нагрузка на MongoDB | 100% | ~20% |

Cache Hit Rate (ожидаемый): **70-80%** для `GET /deliveries`
